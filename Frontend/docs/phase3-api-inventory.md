# Inventario de contratos — frontend Fase 3

Inspección: Angular 22.2.5 / Material 22.2.6, TypeScript 6.0.3, Node 24.15.0; Fases 1/2 reales, sesión/MFA, CSRF, ResourceApi, Signals, guards y UI compartida. Baseline: 33 unitarias/HTTP y lint de 75 archivos aprobados. No se actualizan dependencias principales. Skill leída de Downloads/SKILL fase 3.md; los auxiliares references/templates de la skill frontend no fueron suministrados. Se cotejaron las referencias existentes del backend con su código real.

Paginación: `{count,next,previous,results}`, 20 por defecto, máximo 100. Proveedores orden nombre/id, compras fecha/id descendente, movimientos fecha/id ascendente, stock nombre/id. No se envía ordering arbitrario. Días desde/hasta inclusivos en America/Lima. RUC es texto opcional hasta 20 sin unicidad/checksum legal: la UI no inventa validación tributaria. Detalles de compra tienen cantidad string NUMERIC(14,3) positiva y costo_unitario string NUMERIC(12,4) no negativo; Django rechaza números JSON. Unidad debe coincidir con la vigente del artículo. Al editar borrador se reemplazan las líneas de forma atómica; compras recibidas/anuladas no se editan.

Adaptaciones mínimas documentadas antes de implementar, sin DDL:

- POST compras con Idempotency-Key opcional por compatibilidad; la nueva UI siempre lo envía y conserva la misma clave para reintentos de una intención. Se almacena hash/ID en auditoría existente bajo bloqueo transaccional; primera respuesta 201, replay 200, payload distinto 409. La recepción conserva su protección independiente por ID. No se presume unicidad legal global de numero_documento, que el esquema no impone.
- GET `/api/inventario/stock/resumen/`: conteos globales activos, bajo mínimo, agotados, sin movimientos y últimas entradas/salidas autorizadas. No suma cantidades de unidades incompatibles ni produce KPIs financieros.
- GET `/api/inventario/stock/usos-receta/?articulo={id}`: paginación de recetas donde aparece el artículo; exige además view_servicios.
- Campos aditivos de lectura en stock: sku,categoria_id,categoria_nombre,activo,unidad_id; operador registrado_por_id en movimientos. No se inventan nombres de personas ausentes.

Alertas de vencimiento existentes solo reflejan fechas de detalles recibidos con existencia_lote=null. No se presentan como alertas fiables de lotes con saldo vigente; la UI limita alertas operativas a reposición y documenta esta carencia. No existe devolución a proveedor ni edición/eliminación del ledger.

Recuperación tras recarga: GET `/api/compras/estado-intento/?clave=uuid` retorna `{encontrada,compra}` y GET `/api/inventario/ajustes/estado/?clave=uuid` retorna `{encontrado,resultado}`. Ambas consultas se restringen al actor de sesión; requieren respectivamente view_compras y view_movimientosinventario. Solo se conserva el UUID de intención en sessionStorage, separado por usuario; nunca cuerpos, contactos, credenciales ni tokens. Si el resultado aún no existe, se conserva la misma clave al reenviar: una operación en vuelo podría confirmar después. El saldo de un ajuste recuperado es histórico; la UI vuelve a consultar el stock actual. La pérdida del almacenamiento de la pestaña exige verificar el historial antes de iniciar otra intención.

Las excepciones CSRF de DRF conservan HTTP 403 y se clasifican como `code=csrf`, sin exponer el motivo interno. Una denegación de permisos conserva `permission_denied`.

Errores 400/422 por campo, 403 sesión/MFA/permiso/CSRF, 404, 409 estado/stock/idempotencia/integridad, 429, red y 5xx. Ante timeout de una mutación no se promete fallo definitivo: reintentar con misma clave o consultar el recurso conocido. Toda aceptación funcional y concurrencia se ejecuta en PostgreSQL aislado; no se crean compras/movimientos reales como prueba local.
