## Garantías verificadas en Django

Las mutaciones financieras usan `Idempotency-Key` UUID por actor/operación, hash de destino/cuerpo, transacción y locks compartidos con inventario. La confirmación valida stock agregado de producto más consumos, crea salidas y consumos una vez y finaliza la visita atómicamente. Los pagos rechazan sobrepago, referencias activas duplicadas y falta de verificación manual. Los anticipos se aplican por disponible y saldo de la misma atención. Un replay devuelve el resultado original; Angular obtiene después el detalle actual.

El nuevo endpoint de recuperación consulta la tabla existente `idempotency_records`, esperando el mismo lock financiero. No requiere migraciones ni almacena solicitudes nuevas. Su resultado no incluye nombres, teléfonos, notas, referencias de pago ni `request_hash`. No se interpreta `encontrado:false` como autorización para generar otra UUID: se conserva la clave, incluso después de recargar.

Una solicitud de check-in no confirma identidad o presencia física. Para propuestas de alta, Django exige aviso vigente y revisión presencial antes de activarlas. No se presenta el 202 como prueba de existencia de una ficha. Las respuestas privadas conservan `Cache-Control: no-store, private`.

## Dependencias y alcance

- Configurar `PUBLIC_CHECKIN_URL=https://<dominio-frontend>/registro/`. Se actualizaron las plantillas de entorno, sin sobrescribir configuraciones privadas existentes. La impresión se bloquea si el enlace aún apunta a JSON, no usa HTTPS o no tiene la ruta del formulario.
- El aviso de privacidad comercial, su versión, el dominio HTTPS accesible desde el celular y la revisión de retención siguen siendo requisitos de operación con personas reales. El arnés E2E usa explícitamente aviso y datos sintéticos.
- No falta una API para el flujo implementado. La consulta de recuperación faltante se añadió de forma real y probada. No hay adaptadores simulados en producción.
- Se aplican anticipos ya confirmados; crear agenda y gestionar nuevos anticipos de reservas pertenece a la fase de agenda. Las citas compatibles existentes se enlazan sin crear reservas.
- El backend sí tiene APIs de reembolsos y ajustes comerciales. La devolución integral de una atención confirmada y reposición de inventario no se presenta como una simple anulación: ese flujo no se implementa en esta fase. Anular un error de pago no devuelve dinero ni stock.
- No se ejecutaron migraciones ni escrituras de negocio en Lasheo. Las preparaciones de esquema y datos de prueba se ejecutan exclusivamente en bases temporales aleatorias verificadas por el arnés.
